# Milestone 2A validation plan: Step 1 audit

## Audit status and conclusion

This document records the state of the milestone-1 implementation audited on
2026-07-13, before milestone-2 data, model, or evaluation changes. It is an
audit and validation plan, not evidence that Milestone 2A has passed.

The current result is **not yet a valid answer to the main research question**.
The saved ActMask checkpoint has test IoU `0.6811`, versus `0.6031` for
`ActionProximityMask`, but this is one seed, one fixed threshold, and an
in-distribution test generated by the same simple rule as training. More
importantly, an audit-only scenario recomputation found thresholded paired
consistency of `0.0` for both `opposite_velocity` and `different_timing`.
Consequently, the global result does not prove that the model uses velocity or
action timing. The current recommendation is **no-go for simulator integration**
until the validation gates at the end of this document pass.

The terms below are used deliberately:

- **Proven for the current snapshot** means directly established from source,
  current artifacts, or a deterministic recomputation.
- **Not proven** means that a plausible claim has no adequate current test.
- **Risk** means a possible failure mode; it is not presented as an observed
  failure unless evidence is given.

## Current ground-truth rule

### Scene construction

**Proven for the current snapshot:** each sample has 96 points in three fixed
contiguous blocks:

- 32 target points around `target_center`;
- 24 distractor points around `distractor_center`;
- 40 uniformly distributed background points.

The target has one constant planar velocity sampled at speed approximately
`[0.26, 0.30]`; all target points receive exactly that velocity. The distractor
is static. Background velocities are independent clipped Gaussian values. The
first target and distractor offsets are forced to zero, so their exact centers
are present in the cloud. The action always starts at the distractor center,
the gripper radius is always `0.09`, and the gripper center follows one straight
line segment.

For a pair, `_rng_for_pair(pair_id)` is re-created from
`SeedSequence([dataset_seed, pair_id])`. Both variants therefore have
bit-identical current points. The scenario is deterministically
`SCENARIOS[pair_id % 4]`. Variant differences are:

| Scenario | Held fixed | Changed in variant 1 |
| --- | --- | --- |
| `opposite_velocity` | points and complete action | all base velocities are negated |
| `different_action_direction` | points, velocities, start, duration, radius | action endpoint/direction |
| `different_timing` | points, velocities, spatial path, radius | duration `1.15` to `0.35` seconds |
| `interception_success` | points, velocities, start, duration, radius | endpoint is shifted perpendicular to the intercept |

All current pairs contain variants 0 and 1, share their scenario and points,
and have different masks. Across all three current splits, every variant 0 is
labelled successful and every variant 1 unsuccessful. `success` is derived from
whether any target point is mask-positive; it is not the per-point label.

### Mask equation

For action start `s`, endpoint `e`, duration `T`, radius `r`, point `p_i`, and
constant velocity `v_i`, 16 uniformly spaced synchronous times (including both
endpoints) are used:

```text
t_k = k T / 15
g(t_k) = s + (t_k / T) (e - s)
p_i(t_k) = p_i(0) + t_k v_i
mask_i = 1[min_k ||p_i(t_k) - g(t_k)||_2^2 <= r^2].
```

Thus the label is a discretized, time-aligned moving-sphere proximity rule. It
is not continuous collision detection and contains no acceleration, curved
motion, delayed onset, orientation, robot body, force, occlusion, or sensor
uncertainty. Because `t=0` is included and the action starts at the center of
the static distractor, all distractor points are positive in every current
sample. This observed property is a major benchmark shortcut, not merely a
theoretical concern.

## Train/validation/test split audit

`build_dataset` does not split a master collection. It constructs three
independent procedural datasets:

| Split | Dataset seed | Samples / pairs | Raw `pair_id` values | Samples per scenario |
| --- | ---: | ---: | --- | ---: |
| train | 2026 | 64 / 32 | 0--31 | 16 |
| validation | 2027 | 24 / 12 | 0--11 | 6 |
| test | 2028 | 32 / 16 | 0--15 | 8 |

The following statements answer the leakage questions narrowly and separately:

1. **Can variants from the same actual current pair cross splits?** Not in the
   current config. Each procedural dataset contains both consecutive variants,
   and its even length does not cut a pair. A qualified current scene key
   `(dataset_seed, pair_id)` has zero overlap across splits.
2. **Can the same base point cloud cross splits?** No exact duplicate was found
   in the current config. There are 32, 12, and 16 unique base-point hashes in
   train, validation, and test, respectively, with zero cross-split hash
   intersections.
3. **Can the same current random scene cross splits?** Not under the current
   seeds if a random scene is defined by `(dataset_seed, pair_id)`. The three
   dataset seeds are distinct and those qualified keys have zero overlap.
4. **Can the same raw `pair_id` appear across splits?** Yes. Train/test share 16
   numeric IDs, train/validation share 12, and validation/test share 12. The
   emitted `pair_id` is therefore not globally unique.
5. **Can the same trajectory/scenario family cross splits?** Yes. All four
   scenario families deliberately occur in every split and use the same
   parameter support.

These facts do **not** prove the split implementation is generally leakage-safe:

- Samples expose no `base_scene_id`, `object_geometry_seed`, `scenario_seed`, or
  globally namespaced pair ID. The dataset seed is not part of each sample.
- There is no persisted split manifest, group-aware assignment, or test that
  checks group intersections.
- Config validation does not prohibit equal `train_seed`, `val_seed`, and
  `test_seed`. Setting two split seeds equal would reproduce the same early
  pairs and leak identical scenes.
- Exact tensor-hash separation only establishes that the current files are not
  byte-identical. It does not establish an OOD split or independence between
  the distributions.
- Scenario is a deterministic function of pair index, and all splits sample the
  same geometry, velocity, action, duration, and radius distributions. The
  current test is interpolation under new RNG draws, not held-out dynamics.

The current snapshot therefore has no observed exact train/test scene duplicate,
but the mechanism lacks the identifiers and invariant needed to guarantee this
after the benchmark is extended.

## Baseline information-equivalence audit

All predictors receive the same Python call signature, but they do not use the
same information:

| Predictor | Information actually used | Decision at probability 0.5 | Equivalent to label rule? |
| --- | --- | --- | --- |
| `NoMask` | none | every point is positive because its probability is exactly 0.5 and comparison is inclusive | No |
| `MotionMagnitudeMask` | velocity magnitude only | `||v_i|| >= 0.05` | No: ignores point location, velocity direction, and action |
| `ActionProximityMask` | current point, action start/end, and radius | current spatial distance to finite segment `<= radius` | No: ignores velocity, synchronous time, and duration |
| `ActMaskModel` | points, velocities, relative offsets to start/end, and the complete action | learned logit `>= 0` | It receives all varying label inputs, although not the rule itself or the fixed `trajectory_steps` constant |

**Direct answer about `ActionProximityMask`:** the function is passed velocities
and the complete action tensor at its interface, so equivalent information is
available in the dataset. Its implementation discards velocities and duration,
and therefore does not use information equivalent to the ground-truth
generator. This makes it a deliberately weak baseline, not the strongest fair
geometric comparison.

With exact velocities, the action, constant-motion assumption, and known
sampling rule, a parameter-free time-aligned geometric method can reproduce the
current mask exactly. Such a method is absent. When it uses the identical label
sampling and exact dynamics it must be named an **oracle label-rule upper
bound**, not a deployable competitor. A strongest reasonable non-oracle
geometric baseline should also be evaluated using the same noisy or estimated
motion observations made available to ActMask.

Other baseline-specific observations are:

- `MotionMagnitudeMask` has a hand-set threshold placed between the target speed
  and almost all background speeds. It largely identifies target membership but
  cannot distinguish either action or the sign of velocity.
- At the global threshold, `ActionProximityMask` has one false positive in
  6,144 train points, and zero false positives in validation and test. The
  current benchmark therefore contains essentially no geometrically close
  hard negatives.
- On test, `ActionProximityMask` has exactly 512 false negatives. These show that
  the generator does contain future entrants that current-position proximity
  misses, but one easy positive pattern is not sufficient validation.

## Possible leakage and shortcut risks

### What is not directly leaked

**Proven:** `mask`, `success`, `pair_id`, `variant_id`, and `scenario` are not
passed to `ActMaskModel.forward`. Validation labels are not used to compute the
training positive weight, and the checkpoint is selected on validation rather
than test IoU. No direct mask-field leak was found.

### Observed generator shortcuts

The following are present in the current data and can support a high global
score without learning the intended general relationship:

- All 24 distractor points are positive in every sample because the action
  starts at their static center. They contribute 25% of every mask before any
  future reasoning is needed.
- Exactly half of all target points are positive across each split: successful
  variant 0 contains the target, while unsuccessful variant 1 does not. Target
  points are easy to identify by their identical high velocity magnitude.
- Background points are almost always negative (0.70%, 0.73%, and 0.78%
  positive in train, validation, and test).
- Variant 0 is always successful and variant 1 always unsuccessful. Variant ID
  is not an input, but endpoints and the small discrete duration set can be
  correlated with this construction convention.
- The radius is constant, durations take only four values, motion is linear,
  and scenario is tied to `pair_id % 4`.
- Point blocks always occur in target/distractor/background order. The current
  shared pointwise MLP has no explicit index input and cannot directly exploit
  ordinal position, but the ordering is still an avoidable dataset artifact and
  would become exploitable by future index- or sequence-sensitive models.

### Generalization and provenance risks

- The label is a deterministic low-dimensional function of exactly the clean
  features given to ActMask. This is intentional supervision, but the current
  experiment can only show rule approximation, not generalization beyond the
  hand-designed rule.
- There is no held-out geometry family, trajectory family, parameter interval,
  noise regime, or object count. Train and test use the same generator support.
- The visible test JSON can be repeatedly consulted during development. There
  is no sealed test manifest, so human test-set selection is a process risk even
  though it cannot be inferred from source alone.
- A single seed and single short training run cannot distinguish a stable effect
  from initialization variance.
- The checkpoint lacks a full resolved config, dataset/split manifest or hash,
  threshold, source revision/hash, and runtime version. Its relation to the
  current YAML is consistent but incompletely proven by metadata alone.

## Thresholds, loss, and metric semantics

The current thresholds are:

- ground truth: sampled squared distance `<= radius^2`;
- target binarization in metrics: label `>= 0.5`;
- all prediction metrics: probability `>= 0.5` from the YAML;
- `MotionMagnitudeMask`: at probability 0.5 this is speed `>= 0.05`;
- `ActionProximityMask`: at probability 0.5 this is distance `<= radius`;
- `NoMask`: probability is exactly 0.5, so it predicts all points positive.

The same fixed 0.5 probability threshold is used during training reports,
validation checkpoint selection, and test evaluation. Validation IoU selects
the checkpoint, with validation loss as a tie-breaker. There is no validation-
only threshold search, precision-recall curve, average precision, or PR-AUC.
Metrics pool confusion counts over all points (micro averaging); they are not
macro-averaged over clouds or scenarios. A zero denominator returns zero.

The training loss is pointwise `BCEWithLogitsLoss`. The recomputed training
negative/positive ratio is `3566 / 2578 = 1.3832428239`, below the configured
cap of 20, so that exact value is the positive weight. The visualization YAML
also contains threshold 0.5, but the visualization code does not apply it; all
prediction panels show continuous probabilities.

### Checkpoint

Restricted CPU loading succeeds under PyTorch `2.6.0+cpu`; CUDA is unavailable.
The checkpoint is a mapping with:

- epoch 5;
- 12 CPU float32 model tensors;
- AdamW optimizer state;
- seed 2026;
- model dimensions `48 / 24 / 48`;
- validation precision `0.7147`, recall `0.9897`, F1 `0.8300`, IoU `0.7094`,
  and loss `0.4365`.

Those validation values exactly match epoch 5 in
`training_metrics.json`, which is the saved best epoch. This internal agreement
is proven. The checkpoint does not contain enough provenance to independently
prove its dataset seeds, sample counts, temporal resolution, threshold, or code
snapshot. Saving optimizer state is useful for resuming but unnecessary for

## Visualization audit

The visualization correctly uses a headless backend, loads the local checkpoint
on CPU with `weights_only=True`, uses common color limits, and overlays velocity
vectors and the candidate trajectory. The current default PNG shows ground
truth, all three baselines, and ActMask for test sample 0.

Its evidentiary scope is weak:

- it shows only `opposite_velocity`, pair 0, variant 0, success 1;
- it does not show the paired unsuccessful variant;
- panels contain no per-sample IoU, precision, recall, or counterfactual delta;
- the configured threshold is not visualized;
- selection is by manually configured index, not deterministic best/worst or
  baseline-win criteria;
- it contains no OOD or irrelevant-change example.

It is a useful qualitative sanity check, not validation. The current figure
cannot rule out cherry-picking or demonstrate dependence on action and motion.

## Expected weaknesses against the research question

| Required distinction | Current evidence | Audit verdict |
| --- | --- | --- |
| same geometry, different velocity | `opposite_velocity` pairs exist | Present in data, but ActMask test pair consistency is 0.0; not learned at the current threshold |
| same geometry and velocity, different action | direction and interception pairs exist | Mixed: direction pair consistency is 0.5709, interception only 0.1382 |
| same candidate action, different future dynamics | opposite-velocity pairs hold the action fixed | Present in data, but thresholded consistency is 0.0 |
| currently close points that will not contact | current proximity has 0 validation/test false positives | Effectively missing; benchmark does not stress this case |
| currently distant points entering future swept volume | current proximity has 512 test false negatives | Present, but highly regular and coupled to the target block |

Additional expected weaknesses are:

- a moving sphere, straight gripper line, and constant velocity make the label
  analytically recoverable from clean inputs;
- temporal sampling can alias contacts between the 16 samples;
- there is only one moving target, one static distractor, fixed object sizes,
  fixed radius, and nearly fixed target speed;
- distractors are easier than targets and never have misleading high motion;
- no point dropout, position noise, velocity error, partial observation, or
  object identity uncertainty is present;
- the pointwise model cannot use neighborhood, object, or global interaction
  structure;
- global micro metrics over-represent the always-positive distractor and hide
  pair/scenario failures;
- no current result measures calibration, threshold independence, OOD behavior,
  seed variation, or robustness to irrelevant changes;
- the strongest fair geometric comparison is absent.

## Concrete Milestone 2A validation plan

The following order prevents later experiments from legitimizing a leaked or
underspecified benchmark.

### 1. Freeze globally identified grouped splits

Generate a master scenario manifest before constructing variants. Every record
must expose at least `base_scene_id`, globally unique `pair_id`,
`geometry_seed`, `scenario_seed`, `trajectory_family`, and `scenario`. Assign a
single immutable `group_id` representing all variants derived from the same
base scene/pair. Split group IDs deterministically, then instantiate samples;
do not independently regenerate three unnamed datasets.

Required assertions and saved statistics:

- every variant of a group belongs to exactly one split;
- train/validation/test intersections are empty for group ID, base scene ID,
  pair ID, geometry seed, and scenario seed;
- exact base-point hashes are also disjoint as a diagnostic;
- all expected variants are complete within each group;
- split counts, positive prevalence, per-scenario counts, parameter ranges, and
  manifest hashes are saved;
- a deliberately duplicated seed causes the leakage test to fail.

Trajectory families may occur across the normal ID splits for scenario-wise
evaluation, but families designated OOD must be absent from training by an
explicit manifest assertion.

### 2. Harden labels and create diagnostic subsets

Preserve the public tensor interface while adding acceleration, curved motion,
delayed onset, multiple objects, fast non-interacting distractors, static near
misses, future entrants, near-miss actions, varied action timing/duration and
radius, and where practical piecewise gripper paths, dropout, noise, and
imperfect velocity estimates. Randomize point ordering.

Each generated sample should retain latent diagnostic tags, separate from model
inputs, for `near_static_noncontact`, `future_entrant`, `moving_distractor`,
`target`, and `background`. Unit tests must independently recompute selected
trajectories and label boundary cases. Where a numerical sampler defines the
label, compare it against a finer-time or analytic collision calculation to
quantify discretization error.

### 3. Establish fair baseline tiers

Evaluate and document an information matrix for:

1. no mask / all-positive;
2. motion magnitude;
3. current-position action proximity;
4. future-position proximity using observed velocity;
5. minimum point-trajectory/gripper-trajectory distance without time alignment;
6. time-aligned future proximity using the same observable motion estimates as
   ActMask;
7. an exact-parameter, exact-label-rule oracle, clearly excluded from claims of
   deployable superiority.

The primary learned comparison must be the strongest non-oracle geometric
baseline with the same observation quality. On the present exact constant-
velocity data, the label-rule oracle should score 1.0; failure to do so is an
implementation bug. ActMask is not expected to beat that oracle.

### 4. Make evaluation scenario-wise and threshold-independent

Retain per-point probabilities and per-sample metadata. For every model,
scenario, ID/OOD slice, and diagnostic subset, report confusion counts,
precision, recall, F1, IoU, average precision/PR-AUC, positive prevalence,
paired consistency, and success ranking where defined. Report both point-micro
and sample/scenario-macro summaries so the always-positive distractor cannot
dominate.

Select a learned-model probability threshold using validation data only, with a
predeclared objective (primary proposal: maximum validation F1, with the lowest
threshold as a deterministic tie-break). Freeze it before test evaluation.
Average precision is the primary threshold-independent mask metric. Natural
geometric decision boundaries should be reported, and tunable baseline
thresholds must also be selected only on validation data. Save PR curves,
selected thresholds, and the complete selection trace.

### 5. Test feature dependence, not just predictive score

Train Full, NoVelocity, NoAction, and PositionOnly with identical grouped splits,
epochs, and seeds. Evaluate Full with deterministically ShuffledVelocity and
ShuffledAction inputs. Shuffles must be generated from recorded permutations,
must not move labels, and should be reported both within scenario and across
scenario to distinguish reliance from distribution-shift artifacts.

Run at least five deterministic training seeds. Report mean, standard deviation,
minimum, maximum, and every individual run. Before viewing test results,
pre-register a practical effect size. A provisional gate is that Full improves
mean AP or paired-change IoU by at least 0.05 over each matching removed or
shuffled input condition, with the expected direction in at least four of five
seeds. The final frozen criterion must be written to the output metadata; it
must not be chosen after seeing test results.

### 6. Quantify counterfactual behavior

For velocity and action counterfactual pairs, report:

- IoU/F1 between predicted XOR and ground-truth XOR change masks;
- mean probability increase on `0 -> 1` points and decrease on `1 -> 0` points;
- fraction of changed points with the correct signed probability response;
- probability stability on ground-truth invariant points;
- successful-action ranking when success differs.

For irrelevant-change pairs, report mean and maximum absolute probability
change on unchanged relevant points, plus mask IoU before/after. Separately
report recall on future entrants and false-positive rate on current near misses.
Qualitative panels cannot substitute for these numbers.

### 7. Define genuine OOD sets

Choose and save non-overlapping train versus OOD ranges for velocity magnitude,
acceleration, action duration, gripper radius, curvature, point noise, and
distractor count. Tests must compare the sampled values themselves, not merely
config text, and fail on any overlap. Report ID and each OOD axis separately;
do not pool them into one favorable average.

### 8. Automate representative failure visualization

Select examples deterministically from the complete evaluation records: best
and worst ActMask IoU, largest ActMask win and loss versus the strongest
geometric baseline, counterfactual failures, irrelevant-change failures, and
OOD failures. Each figure must show ground truth, strongest baseline, ActMask,
velocity vectors, action trajectory, scenario/seed/group/parameter metadata,
threshold, and numerical metrics. Store the selection rule and sample IDs so
figures are reproducible and cannot be silently cherry-picked.

### 9. Preserve provenance and reproducibility

Every checkpoint/result bundle should record the resolved config, model and
training seed, split-manifest hash, dataset version and parameters, chosen
threshold source, source-tree hash or revision, PyTorch/Python versions, and
checkpoint checksum. Continue restricted CPU checkpoint loading. Save JSON and
CSV scenario results plus a readable Markdown summary under
`outputs/actmask/milestone2/` without deleting milestone-1 artifacts.

## Decision gates for simulator integration

Milestone 2B should remain blocked until all of these are demonstrated:

1. grouped split tests and sampled-parameter audits show no related scene/pair
   or OOD-range leakage;
2. scenario-wise, macro, AP/PR-AUC, and validation-selected-threshold results are
   complete and reproducible;
3. Full consistently degrades when velocity or action is removed or shuffled;
4. velocity, action, and irrelevant-change counterfactual metrics show the
   correct direction and stability, not merely success ranking;
5. results cover nonlinear, multi-object, hard-negative, future-entrant, and
   separately reported OOD cases;
6. five-seed uncertainty is reported without selecting the best run;
7. ActMask is compared honestly with the strongest same-information geometric
   baseline, while the exact label-rule method is labelled as an oracle;
8. deterministic failure visualizations, tests, commands, and provenance are
   complete.

Passing these gates would support simulator integration as the next data-source
validation step; it would still not establish real-robot readiness. The current
snapshot fails gates 2--8 and lacks a durable guarantee for gate 1, so its
metrics must remain toy smoke-test results rather than a research claim.
